# The Widgets board card

The Microsoft Store build of Limvo puts a card on the Windows 11 Widgets
board (Win+W): the main limit of every signed-in service, each with its
pace and reset, in three sizes. The taskbar has room for a few chosen
limits; the card is the overview, so it does not follow the taskbar pins. The installer build has no card, because the board
only shows widgets of packaged apps.

## How it fits together

```
 Widgets board ──COM──▶ limvo.exe (widgets/mod.rs: IWidgetProvider)
        ▲                      ▲
        │ UpdateWidget         │ update_widget(card)
        └──────────────────────┴── flyout window (ui/useWidgetCard.ts)
```

- **One process.** `limvo.exe` is its own widget provider. In the packaged
  build it registers a class object for the provider's class id at start-up,
  on a thread of the multithreaded COM apartment, and keeps it for the whole
  session. When the board needs the provider while Limvo is not running,
  Windows starts `limvo.exe` from the manifest's `com:ExeServer`, which then
  starts as usual and registers itself.
- **The interface words the card.** Translations and the pace live in the
  interface, so the flyout window sends the card's content whenever it
  changes (`useWidgetCard`), as it does for the tray tooltip. The provider
  keeps the latest content, bounds it, and hands it to every pinned widget
  with the template in `src-tauri/src/widgets/template.json`.
- **No state of its own.** Every pinned widget shows the same content, so
  the provider answers `CreateWidget`, `Activate` and a size change by
  sending the latest content, and ignores `Deactivate` and `DeleteWidget`.
- **Actions.** A click on the card opens the flyout (`open`); the larger
  sizes have a refresh button (`refresh`).

## The template

An Adaptive Card 1.5 with data binding. The provider sends `small` (the
first limit), `medium` (three) and `large` (up to six), plus `hasItems`,
`empty` and `refresh`; the template picks by `$host.widgetSize`. Try it in
the [Adaptive Cards designer](https://adaptivecards.io/designer/) with the
host set to Windows Widgets.

## Package manifest

`src-tauri/msix/AppxManifest.xml` declares:

- `com:Extension` with the `com:ExeServer` and the provider's class id,
  `37549728-fbb6-4975-ae5e-047f0ba9d0a2`. It must never change: pinned
  widgets find their provider by it.
- `uap3:AppExtension` named `com.microsoft.windows.widgets`, with the widget
  definition `Limvo_Limits` (small, medium, large, one instance) and the
  picker's screenshots from `src-tauri/msix/widgets`
  (`python scripts/widget-art.py` draws them).
- A `PackageDependency` on the Windows App Runtime 1.8, which carries the
  Widgets API. The Store installs it with Limvo.

## The bindings

The Widgets API comes from the Windows App SDK, not from Windows itself, so
the `windows` crate has no bindings for it. `src-tauri/src/widgets/bindings.rs`
is generated by `windows-bindgen` 0.65 from `Microsoft.Windows.Widgets.winmd`,
which ships with the Windows App Runtime (for example in
`C:\Program Files\WindowsApps\Microsoft.WindowsAppRuntime.1.8_*_x64__8wekyb3d8bbwe`).
It is committed, so builds need neither the runtime nor the generator. To
regenerate it, run `windows_bindgen::bindgen` from a scratch crate with:

```
--in default <path to Microsoft.Windows.Widgets.winmd>
--out bindings.rs --flat --implement
--reference windows,skip-root,Windows
--filter Microsoft.Windows.Widgets.Providers.IWidgetProvider
         Microsoft.Windows.Widgets.Providers.WidgetContext
         Microsoft.Windows.Widgets.Providers.IWidgetContext
         Microsoft.Windows.Widgets.Providers.WidgetActionInvokedArgs
         Microsoft.Windows.Widgets.Providers.IWidgetActionInvokedArgs
         Microsoft.Windows.Widgets.Providers.WidgetContextChangedArgs
         Microsoft.Windows.Widgets.Providers.IWidgetContextChangedArgs
         Microsoft.Windows.Widgets.Providers.WidgetManager
         Microsoft.Windows.Widgets.Providers.IWidgetManager
         Microsoft.Windows.Widgets.Providers.IWidgetManagerStatics
         Microsoft.Windows.Widgets.Providers.WidgetUpdateRequestOptions
         Microsoft.Windows.Widgets.Providers.IWidgetUpdateRequestOptions
         Microsoft.Windows.Widgets.Providers.IWidgetUpdateRequestOptionsFactory
         Microsoft.Windows.Widgets.Providers.WidgetInfo
         Microsoft.Windows.Widgets.Providers.IWidgetInfo
         Microsoft.Windows.Widgets.WidgetSize
```

## Trying it locally

The card needs package identity, so run Limvo from a registered package
layout. This needs Windows Developer Mode (_Settings > System > For
developers_). The test package (`Limvo.Local`) installs beside the Store
version, but only one installed package may declare the provider's class
id: remove the test package before installing a Store version with the card.

1. Quit Limvo.
2. `npx tauri build --no-bundle`, then `./scripts/pack-msix.ps1`.
3. `Add-AppxPackage -Register src-tauri/target/msix/layout/AppxManifest.xml`
4. Start Limvo from the Start menu, open the board with Win+W, choose
   _Add widgets_ and pin **AI plan limits**.

`Get-AppxPackage Limvo.Local | Remove-AppxPackage` removes the test package.
Logs say `widgets: provider registered` once the provider is up.
